# IntradayLab M15 — пункт №09: физическая FINAM READONLY-приёмка (план)

**Состояние: ACCOUNT_OPEN_TOKEN_CREATED / TOKEN_RIGHTS_UNVERIFIED / NOT_RUN / NOT_PASS.** Этот документ — подготовка уже предусмотренного пункта roadmap, а не новый этап, не команда к запуску торговли и не запрос передать секреты в чат.

## Предпосылки

- Отдельный FINAM-счёт **только M15 IntradayLab**, не идентичный действующему H1 по account fingerprint. Собственная область Intel runtime и доступ; **не использовать, не читать и не изменять DPAPI/token/H1 SQLite/Task**.
- Отдельный M15 **READONLY API token**. Вызов `POST /v1/sessions` служит только получению JWT-сессии; затем `POST /v1/sessions/details` должен подтвердить **`readonly == true` и строго один `account_ids == [expected_m15_account_id]`**. Любое несовпадение -> STOP (без GET к чужому счёту).
- До авторизованного локального provision нет права запускать физические REST-вызовы. Никаких секретов/номеров счёта/полных REST bodies или JWT в GitHub, отчётах и чате.
- Для проверки M15 баров пользоваться только `GET /v1/instruments/{symbol}/bars?timeframe=TIME_FRAME_M15&interval.start_time=...&interval.end_time=...` и `GET /v1/assets/{symbol}/schedule`; при необходимости READONLY `GET account/orders`. Запрещены реальные order/SLTP/cancel.
- Официальная REST документация: <https://api.finam.ru/docs/rest/>. Для TIME_FRAME_M15 документирована глубина **30 дней**. Поэтому свеча IMOEXF 09.09.2026 уже вне этого REST lookback на 16.10.2026 и **не должна требоваться** в этом шаге; конфликт разрешён сравнением pinned M5/M15 в [аудите №08](data_intake/STEP08_IMOEXF_M5_CONFLICT_RESOLUTION_20261016.md).

## Один ограниченный READONLY цикл для N4

1. В изолированном M15 процессе зафиксировать время наблюдения UTC/MSK, **только хэш** второго account и точные H1/M15 разделённые корневые пути (проверять локально, не печатать H1 ID).
2. Подтвердить `readonly==true`, точную область одного M15-счёта. Если новый счёт не доступен — `WAIT_ACCOUNT`, не продолжать.
3. Для каждого `USDRUBF@RTSX`, `CNYRUBF@RTSX`, `GLDRUBF@RTSX`, `IMOEXF@RTSX` запросить schedule и ограниченный M15 баровый интервал в пределах последних 30 дней. Сохранить SHA256 обезличенного полного raw OHLCV/timestamp evidence *локально*, в Git только агрегированные временные и количественные параметры после проверки отсутствия персональных данных.
4. На двух последовательных запросах по каждому инструменту подтвердить на реальных ответах, что timestamp относится к **OPEN** M15 (сопоставление с независимыми CSV по точному общему OPEN, OHLCV). Не выставлять `verified_open_labels=True` только потому, что API назвал `bars`; подтверждение должно исходить из actual broker payload.
5. Отдельно подтвердить **публикацию завершения**: смежная следующая свеча OPEN является свидетелем Close предыдущей. Если последней смежной свечи нет, не выпускать новый Close, за исключением доказанного точного окончания торгового окна по schedule. Проверить время торгового окна, клиринг, и несмежные метки без достроения пустых свечей.
6. Сопоставить в пределах 30-дневного перекрытия историю кандидата продолжения с actual FINAM M15. Любое необъяснённое изменение OHLCV, сетки, символа, числа строк -> `STOP_SOURCE_MISMATCH`. Не считать календарные пустоты потерей свечей без отдельного schedule evidence.
7. Предоставить только обезличенный результат: `M15_ACCOUNT_DISTINCT=PASS`, `READONLY_EXACT_BINDING=PASS`, `TIME_FRAME_M15=PASS`, `OPEN_LABEL_VERIFIED=PASS`, `SCHEDULE_AND_CLEARING=PASS`, `COMPLETED_BAR_PUBLICATION=PASS`, `N4_OVERLAP=PASS`, хэши, UTC диапазоны и числа свечей; при первом отказе — FAIL без запуска M15 торговой функции.
