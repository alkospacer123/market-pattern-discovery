# TRL Reproducibility Review

Version: 1.0.2-rc.1 | KMS-03 | RESEARCH_ONLY

## 1. Назначение и границы P0

Проводи полный исследовательский цикл или его независимую проверку, сохраняя доказательную преемственность. Разрабатывай и выполняй вычисления только при отдельном разрешении и только в изолированной research-среде. Этот навык создаёт процедуру, но не полномочия.

- Считай TRL исследованием, а не управлением торговлей. Не изменяй V20, FINAM, заявки, позиции, счета, капитал, scheduled tasks, production-каталоги и LIVE-конфигурацию.
- Не читай и не запрашивай токены, DPAPI, идентификаторы счетов, приватные SQLite, личные журналы и иные секреты. Используй только разрешённые обезличенные входы.
- Не выполняй shell, установку зависимостей, запуск кода, запись в GitHub, PR/issues, изменение памяти или файлов проекта без явного разрешения конкретной задачи. Разрешение на offline research не разрешает GitHub write или LIVE.
- Не применяй ML для формирования сигналов, отбора параметров или кандидатов. Статистические критерии, bootstrap и тесты множественных сравнений допустимы и не считаются ML.
- Не выдумывай запуски, данные, сделки, логи, ревью GPT/Kimi Code или результаты. Недоступный обязательный ZIP/XLSX/OHLCV обозначай `MISSING_DATA`; для отсутствующего бинарного контейнера дополнительно применяй канонический `MISSING_BINARY`, если он предусмотрен текущей методологией. Никогда не заменяй это на PASS.
- При нехватке полномочий останови только запрещённую часть. Продолжи безопасную часть и обозначь итог `PARTIAL` или `BLOCKED`, если критичная цель недостижима.

Выбирай режим до работы:

1. `READONLY_REVIEW` — источники, протоколы, статический анализ и оценка доказательств без запуска.
2. `AUTHORIZED_OFFLINE_RESEARCH` — разработка и выполнение исследования в отдельно разрешённой изолированной среде.
3. `REPRODUCTION` — чистый повторный расчёт точно идентифицированного исследования в отдельно разрешённой изолированной среде.

## 2. Первоисточники и связь с github-source-audit

Начинай с актуального репозитория проекта и текущей цепочки авторитетных документов: корневой AGENTS → Documentation Authority → паспорт TRL → AGENTS TRL → актуальный Start Here → Closeout → Research Registry → Artifact Manifest → Research Methodology и Operating Cycle. Разрешай реальные пути по текущему дереву, а не по памяти; датированные имена и старые ссылки не считай вечными.

Используй `github-source-audit` для repository identity, MAIN/AUDITED_REF, pinned commit, blob/object ID, происхождения SOURCE/DERIVED, статических путей исполнения, зависимостей и тестовых свидетельств. Не дублируй его алгоритм. Получи от него согласованный snapshot и evidence registry, затем проверяй собственную предметную область: исследовательский дизайн, причинность, экономику, статистику и replay.

- Читай первичные отчёты релевантных исследований, frozen protocols, отрицательный индекс и Journal, а не только сводный реестр.
- Воспринимай названия механизмов, исследовательские ID, параметры, распределения капитала и исторические лидеры как изменяемый контекст. Их смысл и статус заново подтверждай по текущему Closeout и оригинальным протоколам на pinned snapshot.
- Для любых TP/Protect/HOLD/EXT-подобных правил восстанавливай точную event-time семантику из исходного протокола и кода. Не выводи правило из сокращённого имени.
- Отделяй `RESEARCH`, `OWNER_SELECTED`, `APPROVED_FOR_IMPLEMENTATION`, `INSTALLED` и `LIVE`. GitHub и TRL не доказывают два последних состояния.
- Фиксируй время среза, commit SHA и object ID источников в отчёте текущей задачи, но не переноси их автоматически в следующую задачу.

## 3. Доказательства и статусы

Используй актуальный словарь TRL. Как минимум различай:

- `SOURCE_VERIFIED` — конкретные байты/Git object проверены; повторный запуск не утверждается.
- `NOT_REPLAYED` — текущая проверка не выполняла расчёт, даже если код прочитан или распарсен.
- `PARTIAL` — доступна лишь часть необходимой цепочки либо совпала только часть контрольных witnesses.
- `MISSING_BINARY` — отсутствует необходимый ZIP/XLSX/иной бинарный артефакт в указанном контексте.
- `MISSING_DATA` — отсутствуют необходимые исходные входы или независимые данные для заявленного вывода.
- `UNKNOWN` — недостаточно доказательств о наличии, отсутствии или состоянии.
- `REPRODUCIBLE_VERIFIED` — в текущей проверке действительно выполнен чистый offline replay, все обязательные входы идентифицированы, контрольные результаты и требуемый ledger сопоставлены, логи сохранены.

Дополнительно маркируй `OOS_COMPROMISED`, `TRUE_OOS_NOT_AVAILABLE`, `HOLD_DATA`, `REJECT`, `CONTINUE`, `CANDIDATE` и `SELECTED_RESEARCH` по смыслу, не подменяя ими статус воспроизводимости. Указывай контекст каждого статуса: GitHub-only, предоставленный архив, конкретная изолированная среда или обезличенный брокерский снимок.

Для существенных утверждений веди evidence ID и locator: путь, commit/object ID или SHA256, строка/таблица/файл, дата наблюдения, выполненная операция и предел применимости. Разделяй наблюдение, историческое свидетельство, вычисленный результат, вывод и гипотезу.

## 4. Сквозной рабочий процесс

1. **Определи вопрос и scope.** Укажи Research/Evolution/Reproduction, объект сравнения, разрешённые действия, исключения и критерий остановки.
2. **Зафиксируй snapshot и преемственность.** Получи pinned источники, текущее решение владельца, прежние гипотезы, отклонённые ветки, уже использованные данные и пробелы воспроизводимости.
3. **Создай frozen protocol до просмотра новых результатов.** Зафиксируй механизм прибыли, правила, данные, сплиты, бюджет экспериментов, исполнение, риск, метрики, статистические критерии и условия REJECT/CONTINUE/CANDIDATE.
4. **Проверь пригодность входов.** Инвентаризируй байты, покрытие, календарь, качество котировок, происхождение и независимость выборок. При отсутствии критичных входов не моделируй их молча.
5. **Проведи Baseline.** Сначала докажи корректность событий, ledger и денежных ограничений; высокий PF не компенсирует ошибку модели.
6. **Выполняй только запланированные Optimization → Robustness → Walk-Forward.** Соблюдай бюджет вариантов и хронологию. Любое новое правило после результата создавай как новую версию протокола.
7. **Допускай TRUE OOS только после проверки независимости и достаточности заранее определённой выборки.** Один раз оцени замороженный кандидат на действительно нетронутых подходящих данных либо честно остановись без TRUE OOS.
8. **Проверь статистическую и экономическую устойчивость.** Оцени неопределённость, множественные испытания, концентрацию, издержки, ёмкость и слабые режимы.
9. **Выполни чистый replay при разрешении.** Сверь не только итоговые метрики, но и сигналы, отказы, заявки, fills, посделочный ledger, cash/GO/equity и контрольные события.
10. **Вынеси раздельные решения.** Зафиксируй исследовательский результат, ранжирование кандидатов, решение владельца и отсутствие автоматического внедрения.
11. **Сохрани Journal и handoff.** Записывай положительные, отрицательные, неполные и прерванные исследования, отклонения от протокола, contamination и точные evidence links.

Не продвигай кандидата по этапам ради завершения цепочки. Досрочный обоснованный `REJECT` — полноценный результат.

## 5. Frozen protocol и контроль исследовательских degrees of freedom

До запуска зафиксируй неизменяемую карточку:

- ID, дату, автора, режим, источник идеи и экономически объяснимый механизм преимущества.
- Инструменты, таймфреймы, торговые календари, timezone, источник данных, период, прогрев, roll/expiry правила.
- Точные сигналы, доступность каждого входа по event time, входы, выходы, SL/TP, защитные переходы, удержание, приоритет одновременных событий.
- Baseline и отличия candidate; единицы сравнения и портфельный контур.
- Капитал по счетам, внешние потоки, риск, ГО, лотность, округление, лимиты, конкуренцию сигналов и обработку отказов.
- Комиссии, spread, slippage, impact, налоги/расчётные сборы при применимости, модели частичных исполнений и ликвидности.
- Train/validation/WF/OOS границы, историю прежнего использования каждого периода и contamination ledger.
- Полное пространство параметров, число вариантов, ручные и автоматические просмотры результатов, критерии остановки и семейство статистических гипотез.
- Primary/secondary metrics, допустимые численные tolerances, обязательные witnesses и заранее определённые gates.

После результата не редактируй исходную гипотезу. Создавай новую версию с родительской ссылкой и считай все данные, повлиявшие на изменение, development-данными. Регистрируй даже незапущенные, но отобранные по известному результату варианты и ручные «проверки идеи».

## 6. Research, Evolution и Journal

### Research — новые преимущества

Ищи трендовые, импульсные и волатильные механизмы с объяснимым источником доходности, а не красивой формой equity. Для каждой идеи указывай первоисточник, почему эффект может существовать, кто оплачивает преимущество, почему оно не исчезает после издержек и почему доступно выбранному исполнению.

- Сопоставляй идею с прежними положительными и отрицательными исследованиями; не перезапускай отклонённую ветку под новым именем без нового механизма или данных.
- Проверяй применимость к конкретному рынку: торговые фазы, контрактные спецификации, roll, ликвидность, ограничения и доступность данных.
- Для новой стратегии используй подходящий рыночный/портфельный benchmark; не создавай искусственно слабый V20 baseline.
- Не требуй обязательного открытия новой системы. При отсутствии сильных гипотез фиксируй это.

### Evolution — улучшение действующих систем

Сравнивай baseline и candidate на одинаковых входных байтах, календаре, исполнении, риске, капитале и издержках. Изменяй только объявленный фактор либо явно описывай факторный дизайн.

- Разделяй диагностику реальных обезличенных результатов и исторический backtest. Не переноси модельный Net/PF в брокерский P&L.
- Восстанавливай влияние изменения через полный хронологический replay, включая последующие лоты, ГО, отказы и портфельные пересечения.
- Оценивай предельный вклад, корреляцию рисков, сложность, операционную надёжность и цену упрощения, а не только прирост прибыли.
- Передавай улучшение лишь как research handoff. Любой diff, релиз, deploy и проверка INSTALLED/LIVE относятся к отдельному разрешённому проекту.

### Journal — необратимая преемственность

Для регулярного сопровождения сверяй текущий Operating Cycle, Roadmap, STATUS и календарь отчётности; не закрепляй их датировки в навыке. В месячном цикле разделяй обзор Research и фактическую Evolution на разрешённых обезличенных отчётах владельца; при отсутствии полного снимка используй `HOLD_DATA`/`NOT_AVAILABLE` для финансовой части, не нули. В квартальных и годовых отчётах соблюдай актуальные критерии, при расчёте доходности учитывай внешние потоки, объявляй метод TWR/MWR или иной обоснованный метод; не складывай PF и проценты отдельных счетов. Не запускай циклы автоматически и не публикуй их без разрешения.

Веди append-only хронологию: идея → frozen protocol → входы → действия → отклонения → результаты → решение → следующий шаг. Сохраняй неудачи, crashes, пустые выборки, противоречия и contamination.

- Не переписывай старое решение или результат задним числом. Добавляй датированное erratum/дополнение со ссылкой на исходную запись.
- Отделяй факт, интерпретацию, гипотезу и решение владельца.
- Веди genealogy идей и реестр просмотренных данных, чтобы следующий исследователь мог доказать новизну и независимость.

## 7. Качество данных, причинность и утечки

### Инвентарь и качество котировок

Сохраняй raw-входы неизменными. Для каждого файла фиксируй происхождение, роль, период, размер, SHA256, схему, timezone, единицы, контракт/roll и все преобразования. Хэшируй отдельно raw, normalized и фактически загруженный движком набор.

Проверяй до расчёта:

- монотонность и дубликаты timestamp, порядок записей, пропуски баров/сессий, неожиданные пересечения периодов и асимметричное покрытие инструментов;
- OHLC-инварианты, tick size, объёмы, нулевые/отрицательные значения, stale prices, экстремальные скачки и расхождения с независимым источником;
- календарь, торговые фазы, клиринг, праздники, сокращённые сессии, переходы timezone/DST, последний доступный бар и границы наблюдаемой сессии;
- спецификации контрактов, multiplier, валюту, expiry, roll, непрерывные ряды и возможные поправки/backadjustment;
- survivor/selection bias, позднее добавленные инструменты, ревизии поставщика и использование информации, которой не было в момент торговли.

Не удаляй выбросы и не заполняй пропуски молча. Заранее определи правило очистки, сохрани исходный и исправленный набор, оцени влияние отдельным сценарием. Нулевое число наблюдений отличай от отсутствия данных.

### ZERO LOOK-AHEAD и data leakage

Для каждого признака построй цепочку `source timestamp → available timestamp → signal timestamp → order timestamp → fill timestamp`. Докажи, что расчёт использует только информацию, доступную к моменту решения.

- Используй только завершённые бары; для MTF фиксируй момент завершения и доступности старшего бара. Не допускай aligned timestamps без as-of логики.
- Проверяй rolling/ centered windows, shift/resample, normalization по всей выборке, future high/low, ex-post разметку эпизодов, сортировку сделок и случайный split зависимых наблюдений.
- Запрещай отбор инструментов, фильтров, границ режимов и top-сделок по будущему результату. Диагностические будущие метки не возвращай в сигнал.
- Моделируй весь поток конкурирующих сигналов по event time. Не удаляй убыточные сделки из готового ledger и не называй оставшееся исполнимой историей.
- Выполняй prefix-invariance тест: результат до момента T не должен меняться при добавлении или изменении данных после T. Дополнительно используй future-perturbation и задержку исполнения как negative controls, если среда это разрешает.
- Проверяй прогрев и состояние на границах периодов: скрытый прогрев на validation/OOS данными тоже может быть утечкой.

Любой просмотр результата периода, повлиявший на правила или выбор кандидата, заноси в contamination ledger. Такой период сохраняй для ретроспективного research, но не называй untouched OOS.

## 8. Исполнение, капитал и риск

Заморозь экономическую модель до оптимизации и исполняй её в едином event-driven ledger.

### Цена и исполнение

- Для `NEXT_OPEN` или иного правила указывай сигнальный бар, следующий доступный Open, пропуски сессий и witness конкретных timestamps.
- Для OHLC с одновременно достижимыми SL/TP задавай детерминированный порядок и минимум один консервативный/alternative stress. Не выбирай порядок по лучшему результату.
- При gap через stop/limit используй цену, доступную по объявленной модели, а не автоматически идеальный уровень заявки.
- Не считай касание лимитной цены доказательством полного fill. Без очереди, ленты и стакана обозначай queue/partial fills как непроверенные условия.
- Моделируй tick rounding, lot step, задержки, отмены, повторные сигналы, частичные fills и остатки заявок только при наличии обоснованных правил/данных.
- Включай все релевантные комиссии и сборы по сторонам, spread, slippage и impact. Стресс-прокси называй прокси, а не историческими брокерскими издержками. Для каждого исследования сверяй действующий контракт TRL и точное определение C1 и альтернативных стрессов; модельные затраты не заменяют фактические комиссии биржи/брокера в Evolution. Не меняй согласованную модель расходов между baseline и candidate.

### Капитал, ГО и лоты

- Веди отдельные счета, cash, realised/unrealised P&L, equity, ГО, резерв, открытый риск и внешние денежные потоки. Явно моделируй взаимодействие счетов только если оно разрешено протоколом.
- Рассчитывай целочисленные лоты из доступного капитала, риска до стопа, multiplier и ограничений ГО. Указывай rounding и поведение при нулевом допустимом размере.
- Используй исторически доступные динамические ГО/спецификации либо маркируй фиксированные значения как proxy. Оцени margin call/liquidation и вариационную маржу, если применимо.
- Обрабатывай сигналы и отказы в хронологическом порядке. Изменение капитала, издержек, ГО или лотности требует полного replay: статический штраф к P&L не воспроизводит последующие входы.
- Не масштабируй Net линейно по капиталу. Показывай max lot, turnover, участие в объёме, отказы по ГО/риску, пиковый совокупный риск и ёмкость по инструментам.
- OHLCV не доказывает глубину стакана и исполнимость крупного пакета. Без наблюдений стакана/очереди/impact вывод о реальной ликвидности оставляй `MISSING_DATA` или `UNKNOWN`.

### Ledger и денежные сверки

Сохраняй как минимум: data/event/available timestamps, instrument, strategy/account, signal, accept/reject reason, order, fill, quantity, price, costs, initial/current risk, SL/TP state, position, cash, ГО, equity и exit reason.

Проверяй инварианты: согласование сигналов → заявок → fills → позиций → закрытых сделок; сумму gross/net и расходов; cash/GO/equity; лимиты риска и одновременных позиций; отсутствие необъяснённых дублей; отдельный учёт открытых позиций на конец. Различай trade-close DD, bar-close MTM DD, intrabar DD и брокерскую equity DD.

## 9. Этапные gates: Baseline → Optimization → Robustness → Walk-Forward → TRUE OOS

### Baseline

Для Evolution/Reproduction воспроизведи эталон на неизменённых данных и конфигурации. Для действительно новой стратегии зафиксируй собственный initial baseline и подходящий benchmark либо честный `NO_BASELINE` для внешнего компаратора; не придумывай аналог V20. Подтверди ключевые события и денежные инварианты до сравнения метрик. Для восстановленного кода различай output parity, ledger parity и source-byte identity; первое не доказывает остальные.

### Optimization

Оптимизируй только на заранее выделенном TRAIN, в пределах экономически обоснованных диапазонов и frozen budget. Включай в число испытаний ручной перебор и прежние запуски по той же гипотезе.

- Предпочитай простые, грубые и интерпретируемые правила; не выбирай узкий изолированный пик.
- После просмотра validation не возвращайся к настройке под тем же статусом выборки. Переводи её в development и создавай новый протокол.
- Не используй PF, один слабый/сильный год или TRUE OOS как целевую функцию повторной подгонки.

### Robustness

Заранее задай стрессы: соседние параметры, задержка сигнала/исполнения, расходы, spread/slippage, ГО, лотность, пропуски/ошибки данных, календарь, подпериоды, инструменты и рыночные режимы.

- Отделяй устойчивость механизма от устойчивости одной точки параметров.
- Проводи полный replay там, где стресс меняет cash, лоты или допуск сигналов.
- Исключение top-K сделок из готового ledger считай только диагностикой концентрации, не новой торговой историей.
- Не превращай Robustness в скрытую Optimization: правила, выбранные по лучшему стрессу, требуют новой независимой проверки.

### Walk-Forward

Зафиксируй rolling/anchored схему, длины окон, прогрев, частоту переоценки и допустимый набор решений до запуска. В каждом окне выбирай правила и параметры только на прошлом, замораживай решение и применяй к следующему хронологическому участку. Если хронологии недостаточно, не имитируй WF. Не допускай пересечения интервалов исходов/удержания через границу TRAIN и оценки: исключай из выбора параметры, зависящие от ещё не завершённых к моменту отсечки событий; при необходимости заранее задавай purge/embargo, причинный прогрев и перенос открытых позиций.

Сшивай результаты без overlap, с согласованным капиталом, издержками и переносом состояния. Показывай распределение параметров и стабильность решений по окнам. Даже корректный WF на многократно исследованной истории остаётся retrospective research, а не автоматически TRUE OOS.

### TRUE OOS

Перед доступом к выборке докажи, что данные не использовались для сигнала, фильтра, параметров, выбора кандидата, ошибок исследования или ручного отбора. Зафиксируй код, конфигурацию, список кандидатов, критерии и SHA входов до открытия результата.

До открытия результатов зарегистрируй минимально экономически значимый эффект (MDE), единицу наблюдения, допустимый риск ошибки, достаточный объём/длительность независимой выборки с учётом кластеризации и мощности либо обоснованный критерий точности, правила остановки и календарь промежуточных просмотров. Не продлевай сбор только до достижения желаемой значимости. При недостаточной мощности/точности маркируй вывод как неопределённый; не выдавай малую forward-выборку за доказательство устойчивости. Оцени кандидат один раз без retune. При нехватке независимой истории используй prospective validation на новых данных с frozen protocol. После любого изменения по OOS результату помечай выборку `OOS_COMPROMISED`; следующий тест требует новой независимой выборки. Не выдавай новый файл, повторный запуск или поздний календарный год сам по себе за TRUE OOS.

## 10. Статистическая обоснованность

Определи estimand и единицу независимости: сделка, сессия, день, месяц, инструмент или портфель. Не считай зависимые и перекрывающиеся сделки независимыми наблюдениями.

- Показывай N, временной охват, exposure, распределение P&L/R, медиану и хвосты, выигрыши/потери, turnover, DD и результаты по годам/инструментам/режимам. Среднего и PF недостаточно.
- Рассчитывай доверительные интервалы для primary effect и разницы candidate−baseline. При автокорреляции/кластеризации применяй обоснованный block/stationary bootstrap по времени и портфельным кластерам либо подходящую зависимую оценку; сохраняй совместную зависимость инструментов.
- Учитывай все множественные испытания, включая скрытые и ручные. Используй подходящий family-wise/FDR метод, White Reality Check, SPA или аналог; объясняй выбор и семейство гипотез, не выбирай метод по желаемому p-value.
- Отделяй статистическую значимость от экономической: размер эффекта после издержек, DD, ёмкость, операционная сложность и доверительный интервал должны поддерживать решение.
- Не экстраполируй Sharpe/доходность механическим корнем из времени при зависимости и нестационарности. Для DD показывай путь, определение и неопределённость; одна максимальная DD не является верхней границей будущего риска.
- Оценивай концентрацию по крупнейшим сделкам, инструментам и режимам, устойчивость к leave-one-out/block удалению и риск тяжёлых хвостов. Не превращай диагностику в отбор удачных правил.
- Для фактической торговли следуй действующему Operating Cycle: если нет обеих сторон распределения закрытых net-сделок, PF = `NOT_AVAILABLE` / `UNDEFINED`, не 0; для исследовательского replay заранее объявляй допустимое `INF`/`UNDEFINED` при нулевой сумме убытков и не ранжируй неинформативный PF как доказательство edge. Не вычисляй метрику по неполным данным без метки `PARTIAL`.

Слабая выборка не доказывает отсутствие edge; она ограничивает вывод. Равным образом отсутствие значимости не компенсируй дополнительным перебором до получения желаемого результата.

## 11. Воспроизводимость и независимый replay

### Изолированная среда

Используй только отдельно разрешённую research-среду без production mounts, брокерских endpoints, токенов и scheduled tasks. Разрешай запись лишь в выделенный research workspace; сеть отключай, если она не необходима и не разрешена. Проверяй архивы на безопасные пути и состав до распаковки, не запускай содержимое автоматически.

Зафиксируй ОС/архитектуру, runtime, зависимости и их resolved versions/hashes, entrypoint, конфигурацию, locale/timezone, seeds, переменные окружения без секретов, доступные ресурсы и порядок команд. Lockfile не заменяет проверку фактически использованных зависимостей.

### Манифест и chain of custody

Для SOURCE, DERIVED и входов веди manifest: relative path, роль, размер, SHA256, источник, commit/object ID при применимости, преобразование и создатель. Не смешивай Git blob SHA1, commit SHA и SHA256 байтов. Записанный ожидаемый хэш не равен вычисленному: вычисляй фактически разрешённым способом.

Сохраняй frozen protocol, исходники, raw/norm manifests, run configuration, stdout/stderr, exit status, время начала/конца, warnings, ошибки, output manifest и hashes. Для детерминированного расчёта выполни второй чистый запуск и сравни outputs; различай byte equality и заранее заданную численную tolerance.

### Уровни проверки

1. **Source inspection** — прочитаны код/отчёт/манифест; статус запуска `NOT_REPLAYED`.
2. **Same-code clean replay** — запуск из новой распакованной копии без старого state/cache; сопоставлены обязательные witnesses.
3. **Cross-environment replay** — повтор в другом чистом окружении с зафиксированными различиями.
4. **Independent recalculation** — независимая реализация критичных расчётов или отдельный verifier по raw inputs и frozen protocol.

Не называй пункт 4 простым повтором того же скрипта. Независимый verifier должен пересчитывать ключевые сделки/метрики, а не лишь читать DERIVED CSV.

### Обязательные witnesses

Сверяй количество и хэши входных баров, сигналов, принятых/отклонённых сигналов, заявок, fills и закрытых сделок; причины отказов; Net/PF/DD с явными определениями; финальные cash/GO/equity; посделочный ledger; выбранные граничные события входа, gap, SL/TP, защитного перехода, удержания, частичного fill и принудительного выхода.

Совпадение только Net/PF/N при отсутствии требуемого ledger = `PARTIAL`. Расхождение фиксируй по первому событию, а не маскируй итоговой близостью. При crash, timeout, silent skip или неполном периоде не присваивай PASS. `REPRODUCIBLE_VERIFIED` ставь только на фактически воспроизведённый scope, не на всё исследование автоматически.

## 12. Объективный выбор кандидатов

Сначала применяй обязательные admissibility gates: корректные данные и причинность, исполнимая экономическая модель, отсутствие неучтённой утечки, достаточная воспроизводимость и заранее заданные ограничения риска. Провал обязательного gate не компенсируй высоким Net/PF или взвешенным score.

Затем сравнивай допустимых кандидатов по заранее объявленным измерениям:

- экономический эффект после издержек и его доверительный интервал;
- DD и хвостовой риск, регулярность по режимам/инструментам, наихудший обоснованный сценарий;
- устойчивость к параметрам, задержкам, расходам, ГО, данным и ёмкости;
- портфельный предельный вклад, корреляция и концентрация прибыли/риска;
- число степеней свободы, поправка на все испытания и качество WF/OOS доказательств;
- операционная простота, наблюдаемость и риск ошибки реализации.

Используй dominance/Pareto-анализ и показывай чувствительность ранжирования к допущениям. Не своди решение к одному композитному баллу, если он скрывает критический недостаток. Лидера по одной метрике называй лидером только по этой метрике и scope.

Разделяй статусы решения:

1. `RESEARCH_LEADER` — расчётный лидер по явно указанному критерию на конкретном срезе.
2. `CANDIDATE` — прошёл применимые исследовательские gates; ещё не выбран владельцем.
3. `SELECTED_RESEARCH` / `OWNER_SELECTED` — зафиксированное решение владельца для исследовательской целевой конфигурации.
4. `APPROVED_FOR_IMPLEMENTATION` — отдельное явное разрешение на подготовку/внедрение конкретного изменения вне TRL.
5. `INSTALLED` и `LIVE` — только независимые свежие доказательства профильного проекта, никогда не следствие research отчёта.

Владелец вправе выбрать не лидера по Net/PF ради риска, устойчивости или простоты. Сохраняй исходные метрики и более раннюю рекомендацию, добавляя новое решение без переписывания истории. Не объявляй выбранную сборку лучшей по каждой метрике.

## 13. Автономная работа при недоступности GPT

Не останавливай разрешённую исследовательскую работу только из-за отсутствия GPT. Самостоятельно выполняй обзор первоисточников, genealogy идей, постановку гипотез, frozen protocol, инвентарь данных, статический аудит, разрешённую разработку и offline replay, статистический анализ, research report и Journal draft.

- Не имитируй диалог, согласование или peer review отсутствующего участника. Ставь `EXTERNAL_REVIEW_NOT_PERFORMED`, если оно требовалось.
- Отдельный clean replay и независимый verifier усиливают доказательность, но не становятся человеческим/внешним ревью автоматически.
- Не расширяй полномочия в автономном режиме. Запрашивай только недостающие разрешённые входы, решение владельца или отдельное разрешение.
- При нехватке данных подготовь максимально полезный `PARTIAL`: точный список требуемых файлов/периодов/ожидаемых hashes из авторитетного manifest, готовый frozen protocol, runbook и незаполненную witness-матрицу. Не заполняй ожидаемые ячейки как actual.
- В handoff передавай pinned snapshot, protocol hash, входы/манифесты, среду, выполненные команды и логи, фактические outputs, первое расхождение, contamination ledger и открытые вопросы.

## 14. Обязательный формат результатов

### Research / Evolution report

Используй компактную структуру, опуская только действительно неприменимые разделы с причиной:

1. ID, дата, режим, scope, разрешения и статус завершения.
2. Pinned source snapshot и evidence registry.
3. Гипотеза, механизм прибыли, baseline/candidate и frozen protocol hash.
4. Данные: raw hashes, покрытие, качество, преобразования, contamination/OOS статус.
5. Причинность и исполнение: event-time цепочка, календарь, SL/TP/gap/partial-fill правила.
6. Капитал: счета, риск, ГО, лоты, издержки, ликвидность и инварианты.
7. Результаты этапов Baseline/Optimization/Robustness/WF/TRUE OOS с фактически достигнутым этапом.
8. Статистика: effect size, интервалы, зависимость, множественные испытания, концентрация и чувствительность.
9. Replay: среда, логи, witness-матрица expected/actual/difference/status, ledger и output hashes.
10. Решение: REJECT/CONTINUE/CANDIDATE/HOLD_DATA, research leader отдельно от owner decision, LIVE unchanged.
11. Ограничения, отрицательные результаты, MISSING_DATA/UNKNOWN и следующий проверяемый шаг.
12. Journal entry и handoff links.

### Witness-матрица replay

Для каждого контроля записывай:

`EV-id | scope/scenario | expected source | expected | actual | tolerance | first differing event | ledger/output locator | PASS/FAIL/PARTIAL/NOT_REPLAYED`

Включай отдельно входные барные hashes/counts, сигналы, отказы, заявки, fills, сделки, Net/PF/DD, cash/GO/equity, граничные события и итоговый ledger hash. Ожидаемое значение из отчёта помечай `REPORTED_EXPECTED`, а не собственным наблюдением.

### Journal entry

Фиксируй timestamp, автора/режим, pinned refs, вопрос, protocol version/hash, фактические действия, данные и их первый доступ, результаты включая отрицательные, отклонения, решение и владельца решения, незакрытые риски и ссылки на доказательства. Для исправления создавай новую запись со ссылкой на исходную.

## 15. STOP и самоконтроль

Останови продвижение кандидата при доказанном look-ahead, неразрешимом contamination, отсутствии критичных данных, несогласованном ledger, нарушении денежных инвариантов, невозможности воспроизвести baseline или запросе неразрешённого LIVE/GitHub действия. Безопасную независимую часть заверши как `PARTIAL`; при критичном провале всей цели используй `BLOCKED`.

Перед выдачей проверь:

- Актуальный pinned snapshot подтверждён, источники и первичные отчёты не заменены памятью или сводкой.
- Полномочия не расширялись; никакие LIVE/V20/FINAM/GitHub/память не изменены без разрешения.
- Frozen protocol существует до новых результатов; все варианты, ручной перебор и отклонения зарегистрированы.
- Причинность доказана по available/event time; MTF, прогрев, сессии и конкурирующие события проверены.
- Raw bytes, normalized data и фактически использованные входы различены и хэшированы.
- Исполнение, gap, SL/TP, лоты, ГО, издержки и ликвидность не подменены оптимистичными молчаливыми допущениями.
- Изменения капитала/расходов/ГО проверены полным replay, а не статическим штрафом.
- TRUE OOS действительно независим либо честно отсутствует; WFA и повторный запуск не названы TRUE OOS.
- Зависимость наблюдений, множественные испытания, неопределённость и концентрация учтены.
- Source verification, запуск, same-code replay и независимый пересчёт не перепутаны.
- Итоговые метрики подтверждены ledger и денежными инвариантами; первое расхождение сохранено.
- Отсутствующие входы, crashes, skips и отрицательные результаты видны; ни один UNKNOWN/MISSING_DATA не превращён в PASS.
- Research leader, CANDIDATE, OWNER_SELECTED, implementation approval, INSTALLED и LIVE разделены.
- Journal сохраняет преемственность без заднего редактирования; handoff позволяет другому исследователю повторить именно этот scope.

## 16. Critical Operations Contract

Перед критической TRL-задачей прочитай `recovery/CRITICAL_OPERATIONS_CONTRACT.md` и применяй `COC-TRL-*` вместе с frozen protocol и первичными отчётами. Не дублируй матрицу в исследовательском протоколе.

- Ограничивай `REPRODUCIBLE_VERIFIED` фактически воспроизведёнными code bytes, входами, конфигурацией и witnesses.
- Не присваивай source-byte identity недоступному оригинальному R097 engine по восстановленному коду, output parity или ledger parity. Указывай `SOURCE_BYTE_IDENTITY_NOT_PROVEN` и точный replay scope.
- Не расширяй replay до untouched TRUE OOS, implementation approval, INSTALLED или LIVE. При `SOURCE_DRIFT`, отсутствующих originals или несогласованном ledger останови продвижение кандидата.
- Контракт не разрешает запуск, GitHub write, V20/FINAM изменения или доступ к секретам.
