## Общая архитектура Trading Systems — контекст для всех трёх проектов Kimi

Это долговечная карта взаимодействия, а не снимок текущего LIVE и не разрешение на доступ. Три проекта — части одной инфраструктуры. Владелец одновременно руководит разработкой, исследованиями и эксплуатацией.

**Производственный контур.** Intel — выделенный компьютер на Windows, используемый как локальный торговый сервер. В `C:\V20Lab` размещена V20 Trading System M15: три автономных программных робота V20-Shallow, V20-OBV, V20-Inside, каждый связан со своим отдельным счётом FINAM. Роботы реализуют утверждённые алгоритмы, получают необходимые рыночные данные, рассчитывают сигналы, размер позиции и защиту и при разрешённой торговле взаимодействуют с FINAM/MOEX. Их исполнение — локальный программный контур, не чат и не генерация торговых сигналов ИИ. Работа чата не должна быть обязательным условием работы торгового ядра. На Intel также размещён Control Center (`C:\Control Center`, документированный loopback UI `http://127.0.0.1:8502`) — операторская панель для наблюдения за V20 и разрешённых управляющих операций. CC не является отдельной стратегией, торговым движком или источником broker truth; READONLY refresh не равен управляющей команде. Исторические H1 `C:\TradingSystemLab` и M15 `C:\IntradayLab` — отдельные прежние системы/источники и сохраняемые библиотеки; не запускать их автоматически. Действующие пути и версии уточнять по паспортам; текущие процессы, позиции, заявки, защита и разрешение торговли требуют свежего отдельного evidence, не выводятся из этой карты.

**Исследовательский контур.** Trading Research Lab — RESEARCH, не четвёртый торговый робот и не компонент LIVE. Research ищет и проверяет торговые гипотезы; Evolution анализирует предоставленные подтверждённые результаты работающих роботов и кандидаты на улучшение; Journal сохраняет историю, включая отрицательные результаты и решения. Исследования и изолированные воспроизведения опираются на исторические данные, оригиналы артефактов и проверяемую методологию. Идея TRL проходит исследовательскую приёмку и решение владельца, затем при необходимости становится отдельной задачей разработки V20/CC; исследование само не меняет установленные системы. Не предполагать наличие отдельной установленной папки TRL на Intel или доступность всех оригиналов в GitHub.

**GitHub и знания.** Один общий репозиторий `alkospacer123/market-pattern-discovery` хранит исходники, релизные патчи, контракты, тесты, документацию трёх проектов и историю решений; `alkospacer123/market-pattern-data` — отдельный репозиторий данных. GitHub — канонический источник принятого SOURCE, не зеркало фактического Intel и не источник текущего состояния FINAM. MAIN, Draft PR, DERIVED, INSTALLED, LIVE, RESEARCH и ARCHIVE различаются. Merge не устанавливает обновление на Intel. Не заменять установленный код одним файлом из MAIN без проверки релизной сборки/патчей. GitHub, память ИИ и резервная копия — разные вещи.

**ИИ и взаимодействие.** GPT/ChatGPT и Codex — существующая инженерная среда; Kimi — независимая дополнительная среда, способная продолжить работу при недоступности GPT после подтверждённой квалификации. Ранее GPT анализировал задачу, разрабатывал изменения/пакеты/команды, а владелец вручную выполнял утверждённые действия на Intel и возвращал результаты для проверки. Целевая модель: профильный Chat координирует задачу и выбирает исполнителя Work или Code; исполнитель делает только разрешённые действия и возвращает проверяемый результат в Chat через KMS-05. GPT и Kimi могут взаимно передавать работу и проводить независимое non-author review. Владелец остаётся единственным источником операционных разрешений. Прямое автоматическое управление приложениями Chat → Work/Code и единая память не предполагаются. Remote Control с телефона — интерфейс управления агентом, не предоставление доступа к LIVE.

**Граница разработки и эксплуатации.** На Intel выделена исходная Git-копия `C:\KimiSandbox\market-pattern-discovery` для согласованной source-only работы; это не production и не OS sandbox. Отдельно должны быть установлены технические границы разрешённого исполнителя для запуска тестов/кода (I0–I4). Цепочка изменения: задача владельца → анализ исходников → отдельная ветка и разработка → разрешённые изолированные тесты → независимое ревью → решение владельца о Merge → отдельный проверенный пакет установки и отдельное решение владельца → контролируемая установка и проверка. Производственный доступ, FINAM/DPAPI, реальные счета и приватные базы не входят в допуск адаптации Kimi. Никакой автоматической установки, ARM/HALT, брокерских команд или повторов неизвестных операций. При неопределённости сохранить UNKNOWN/BLOCKED и остановить затронутую часть.

**Долговечность.** Конечная цель — независимость трёх проектов от конкретного оборудования, GitHub и обоих ИИ. Финальный автономный backup и проверенный cold restore — отдельный заключительный этап после квалификации Kimi. Не считать существующие копии доказанным восстановлением.

## Operating model — Chat / Work / Code routing

Общая модель работы для V20, Control Center и TRL. Профильный Chat — предпочтительная точка постановки задач, координатор и аналитик; Work и Code — самостоятельные агентные исполнители с пересекающимися возможностями. Владелец определяет цель, приоритет, scope и разрешения. Chat не является обязательным посредником: прямое задание Work/Code допустимо, если scope и допуск установлены. Никакая автоматическая оркестрация между приложениями, общая память, одинаковый набор инструментов или permissions не предполагаются без отдельной проверки.

- **CHAT:** решить задачу самостоятельно, если достаточно доступного контекста и разрешённых инструментов (анализ, архитектура, исследование, GitHub READONLY, ревью, планирование). Не делегировать ради делегирования.
- **WORK:** предпочтительный универсальный исполнитель для разрешённых локальных файловых операций, сбора обезличенных диагностических данных, таблиц и отчётов, выполнения проверенных процедур и команд, упаковки/инвентаризации, работы с документами. Может также разрабатывать и тестировать в отдельно допущенной среде. Установка проверенного пакета возможна только после всех применимых технических gates и отдельного решения владельца; текущая квалификация не даёт такого допуска.
- **CODE:** предпочтительный специализированный исполнитель при сложном изменении исходников, Git/diff, отладке, разработке модулей, сложных воспроизводимых тестах и инженерных PR; только в согласованном scope и проверенной среде. Не считать его автоматически более компетентным или безопасным, чем Work.
- Для каждого существенного задания координатор указывает рекомендуемую среду, краткую причину, требуемые инструменты/доступ, разрешённый scope и ожидаемое доказательство результата. При равной пригодности выбирает более простой, безопасный, эффективный по качеству, времени и расходу ресурсов путь. Если задача охватывает несколько сред, выделяет только необходимые независимые этапы; не дублирует работу и не запускает конкурирующие writes.
- При переходе между средами использует [KMS-05 ai-engineering-handoff](skills/ai-engineering-handoff/SKILL.md) после принятия соответствующей редакции: task, checkpoint, pinned refs, permissions, boundaries, evidence, expected result и STOP conditions. Если автоматическая передача не подтверждена, готовит компактное задание для ручной передачи владельцем. Исполнитель возвращает проверяемый результат, а не только PASS; координатор сверяет evidence, при необходимости запрашивает независимое non-author review, и продолжает с подтверждённой точки.
- Выбор исполнителя НЕ является предоставлением прав. Общий AGENTS, проектный контракт, [Windows access gate](WINDOWS_WORKSPACE_AND_ACCESS.md) и действующая программа квалификации имеют приоритет. Work и Code отдельно проверяют доступ, актуальность источников, permissions и реальные границы изоляции. Intel source checkout не OS sandbox. До I0–I4 — только разрешённый source-only/read-only режим; никакого исполнения, установки, доступа к production, секретам или брокеру по одному факту выбора агента. Merge, deploy, ARM/HALT и LIVE требуют отдельных допусков владельца. Не повторять операции с неизвестным исходом.

Модель выбора среды — рабочая методология, не результат сравнительного испытания. Окончательные предпочтения уточнять по уже запланированным практическим задачам G4–G9, без новых повторных экзаменов и без ослабления обязательной отдельной квалификации Code, Work, mobile routes и GPT-OUTAGE. Не изменяет программу Recovery или ранее принятые версии Skills. Исторические статусы выше относятся к датированным срезам.
