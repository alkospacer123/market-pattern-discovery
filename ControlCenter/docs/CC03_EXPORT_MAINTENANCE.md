# CC-owned exports: bounded stop and manual maintenance

Runtime retention remains **DISABLED / NOT ACCEPTED**. No deletion routine or production-log cleanup exists. The publisher refuses a new snapshot before creating a temp when the directory would exceed 2048 total entries (including pending temp/foreign files), or 256 MiB summed leaf bytes plus this snapshot. Unexpected directories/symlinks fail closed; each payload is <=128 KiB. Receiver discovery is likewise bounded. This is not an NTFS disk quota against another writer; provisioning must allow only the dedicated CC exporter to write and must prevent overlapping exporters. An external file growth/race or changed ACL invalidates the accepted layout, not a reason to delete anything.

When full, publication stops and the panel ages to STALE/UNKNOWN. No H1 process, Task, JSON, SQLite/WAL, authorization or journal is touched. At an illustrative one snapshot/10 seconds, capacity is less than six hours, so bounded stop must remain visible and an operator must plan maintenance; no claim of unattended long-term readiness.

## Conservative operator procedure, not performed by this PR

1. Inspect only the existing CC-owned fixed export root and review its recorded NTFS volume/file identity, owner and full effective role ACL against approved policy. If path/identity/ACL/reparse/link checks fail, **STOP; do not move or delete data**. Do not substitute another source directory or follow a junction. No H1 permissions/state change is required or authorized.
2. Stop **only the independent CC exporter scheduling/process and CC panel readers** using their own previously approved lifecycle. Never stop H1 to service CC. Confirm no remaining CC reader/exporter instances and no open handles to the CC export set using an independently approved Windows administration method. If handle ownership/closure is uncertain, STOP. Do not use force-close/delete-on-close or delete open files.
3. Preserve the entire export set as an offline archive under a separately verified CC-owned destination or external maintenance storage, including all completed payloads, their names/digests, latest record, root identity/ACL evidence and timestamps. Copy/verify every intended preserved file before considering a directory rotation. If capacity/verification fails, leave the original intact and keep exporter stopped. No online deletion is part of this procedure.
4. Only after a separately reviewed operator maintenance decision and verified closed handles, archive the old **whole CC export directory without deleting its contents**, provision a new empty CC export directory with the existing least-privilege role matrix, pin its new NTFS root identity in both private observer and trusted receiver policies, and independently revalidate ACL/provenance. Directory rename may fail if a handle remains; treat failure as a stop, never force it. Do not silently reuse the old root pin.
5. Preserve the last digest-confirmed snapshot in the archive until a new approved source-bound snapshot has been published and read/verified. Do not relabel the old snapshot's timestamps or promote it to current. Restart only CC, confirm stale/unknown semantics and intact H1 evidence. Disposal of verified offline archives, disk quota and automated deletion require a separate retention design/NTFS acceptance; this PR does not implement or authorize those deletions.

Native tests cover byte/entry stops before writing, preservation of an open sole completed snapshot, preservation of outside files, root substitution, reparse/hardlink rejection and immutable open-reader publication. They do **not** certify runtime cleanup. The safe current behavior under identity/ACL/disk errors is no new publication and no removal of existing evidence.
