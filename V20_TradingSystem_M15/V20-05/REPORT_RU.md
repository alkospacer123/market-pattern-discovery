## Принудительное завершение и восстановление

Дочерний интерпретатор останавливался через `Popen.kill()`, без `close`,
обработки исключения или штатного освобождения SQLite/instance lock.
Следующий запуск использовал тот же broker book и SQLite.

| Точка OS kill | POST после restart | Результат |
|---|---:|---|
| Решение заявлено, сигнал получен, intent ещё нет | 0 | Возможен пропуск одного входа; исторический NEXT_OPEN не исполняется поздно |
| Reserve + quota + intent закоммичены, POST ещё нет | 0 | `UNCERTAIN_POST_NO_RETRANSMIT`, входы запрещены, резерв сохранён |
| FakeBroker принял POST, ответ ещё не дошёл | 1 | Найдена та же заявка; ACK не считается fill |
| ACK принят, fill ещё нет | 1 | Нет выдуманного исполнения или повторного входа |
| Fill сохранён брокером, SLTP ещё не установлен | 2 | Restart подтверждает fill и устанавливает один SLTP 100% |
| SLTP принят брокером, ACK ещё не дошёл | 2 | Найден существующий стоп, повторного SLTP POST нет |

Во всех шести случаях `PRAGMA integrity_check = ok`, повторных client IDs нет.
В контрольной модели между fill и recovery действительно существует окно без
стопа; испытание доказывает восстановление защиты, а не атомарность двух
брокерских операций. Время такого окна на реальном FINAM не проверено.

В отдельном опыте все три робота одновременно приняли синтетический LONG CNY.
Каждый создал собственные entry+SLTP (2 POST). Второй экземпляр OBV заблокирован.
Shallow убит ОС; SHA256 book двух других счетов не изменились. OBV и Inside
продолжили работу в исходных процессах; Shallow восстановился в новом.
Все три закрылись перед третьей наблюдаемой сессией: по 3 POST, позиции нулевые,
денежные резервы освобождены, стоп отменён после подтверждения flat.
PID и результаты каждого процесса сохранены в JSON.

Процессные fault fixtures используют явно синтетические сигналы/цены и
проверяют инфраструктуру. Это не новые исторические сигналы и не экономический
replay. Соответствие frozen отдельно подтверждается неизменными источниками
и опубликованной parity. Полный N4: USDRUBF, CNYRUBF, GLDRUBF, IMOEXF.

## Обнаруженная ошибка и исправление

Новый тест сначала **FAIL/ERROR**: `request_frozen_exit()` прекращался с
`PROTECTION_UNCONFIRMED_NO_RETRANSMIT`, даже когда позиции и fills уже сверены.
Минимальное исправление в V20 сохраняет halt новых входов и не повторяет
неизвестный POST стопа, но позволяет закрыть подтверждённый остаток позиции.
При неизвестном ENTRY/EXIT POST, чужом ордере или конфликте позиций блокировка
сохраняется: безопасное количество не выдумывается.
Общий цикл также сохраняет исходный time exit после restart с отсутствующим
стопом и продолжает обслуживание остальных подтверждённых позиций.
Тесты запрета новых входов, отсутствия stop retry и выхода — PASS.

Отказ/отсутствие подтверждения SLTP — явно внесённый аварийный сценарий:
такая позиция **не объявляется защищённой**. Повторная установка неизвестного
стопа вслепую не выполняется; требуется диагностика, доступен проверенный выход.
Если активный стоп существует, он сохраняется до подтверждённого flat.
При изменении VWAP частичного fill прежний 100% SLTP сохраняется;
неподтверждённая замена останавливает новые входы.

H1 kill-switch loader/writer/atomic halt переиспользованы без изменения H1,
в `<V20Lab>/<robot>/safety/`. Историческое имя/schema H1 сохранено только как
формат файла; это не авторизация H1 или FINAM. Начальное `ARMED` создаётся
только для новой явной FakeBroker-модели; существующий HALTED, отсутствующий
или некорректный switch не перевзводится. Kill switch запрещает входы,
не отменяет действующую защиту и не запрещает выход.

## Воспроизведение и команды

Из корня существующего checkout, с уже установленными зависимостями проекта:

```bash
python -m V20_TradingSystem_M15.v20_runtime.offline_acceptance --offline \
  --scratch-base "/external/v20 acceptance" --report /external/ACCEPTANCE_REPORT.json
```

Тестовые SQLite/books/logs создаются во внешнем временном каталоге, включая
пробелы в пути; исходные котировки не нужны. Тот же payload используется в Windows:

```powershell
& .\V20_TradingSystem_M15\V20-05\Invoke-OfflineAcceptance.ps1 `
  -Checkout 'C:\path\market-pattern-discovery' `
  -Python 'C:\path\python.exe' -ScratchBase 'C:\V20Lab\acceptance'
```

Сценарий проверяет Windows Server 2022 и запускает только FakeBroker acceptance.
Три процесса, права чтения/записи, пути с пробелами, OS lock, SQLite, restart,
логи и CLI проверяются теми же адресными сценариями. Временные состояния
изолированы под `C:\V20Lab\acceptance`; установка/включение Tasks отсутствуют.
Отчёт по умолчанию `C:\V20Lab\acceptance\WINDOWS_ACCEPTANCE_REPORT.json`.
Требуется реальный запуск: PowerShell wrapper в этом облаке **NOT RUN**.

Команды для **существующего offline** экземпляра, работают и при удерживаемом
процессом instance lock, не открывают SQLite writer или брокера:

```powershell
python -m V20_TradingSystem_M15.v20_runtime.m15_runner --offline --root C:\V20Lab --robot v20-shallow --status
python -m V20_TradingSystem_M15.v20_runtime.m15_runner --offline --root C:\V20Lab --robot v20-shallow --halt-entries
```

`--status` показывает локальный снимок, не доказывает liveness по старому PID.
Команды не создают путь к LIVE. В V20-05 не добавлена команда автоматического
перевзвода HALTED. READONLY-карточка не участвует в торговых решениях.
