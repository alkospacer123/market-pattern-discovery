# TRL — рабочий регламент: месяц / квартал / год

**Редакция:** 2026-10-31, обновлено по последующему решению владельца.  
**Статус:** APPROVED. Действующий календарь определён [Roadmap 1.1](TRL_Roadmap_1_1.md), [календарём 2027](reports/TRL-CALENDAR-2027.md). Roadmap 1.0 сохранён как исходная редакция в ChatGPT Project; фактические статусы — в [STATUS](STATUS.md).

## 0. Роли, источники, правила

**Ответственный за цикл:** ChatGPT TRL — постановка, анализ, контроль выводов, периодический отчёт, Journal.  
**Техническое исполнение:** Codex — целевые offline-вычисления/документы в существующей ветке/PR, контроль SHA и воспроизводимости.  
**Решения о приоритетах/кандидатах:** владелец проекта. **LIVE:** только отдельный проект/чат; из TRL никаких изменений FINAM, токенов, SQLite, Windows Tasks, заявок, торгового кода.

**Источники:** GitHub-исследования, новости трейдинга и алготрейдинга, научные и профессиональные публикации, профильные форумы, технологии, изменения рынков и новые возможности; для реальных финансов V20 — вручную предоставленные пользователем отчёты Финам по трём счетам и, только при адресной необходимости, разрешённые READONLY-данные из отдельного LIVE-проекта. Никакие LIVE-показатели не придумывать. Старые 2018–2026 исследованы многократно и не являются чистым OOS.

**Утверждённый график:** TRL-01 — **каждый месяц**, начиная с **ноября 2026** (в 2026 два цикла: ноябрь и декабрь); TRL-02 — **январь, апрель, июль, октябрь**, впервые январь 2027, с завершённой исследовательской работой в соответствующем месяце, без растягивания на три месяца; **годовые итоги — декабрь**, впервые 2027. TRL-03 отдельным плановым этапом не проводится. **В 2026 TRL-02 и годовые итоги отсутствуют.** Месячные отчёты по завершённому периоду составлять после его окончания и поступления нужных данных, ориентир — первые 5 рабочих дней следующего месяца. Декабрь 2027 — предварительные годовые итоги, финальная финансовая сверка в январе 2028 после брокерских данных. Период и TZ указывать явно (Europe/Moscow для биржевых отметок, если подтверждено источником). Циклы автоматически не запускаются.

## 1. TRL-01 — ЕЖЕМЕСЯЧНЫЙ ЦИКЛ (Research / Evolution / Journal)

**Результат:** один `reports/TRL-MONTHLY-YYYY-MM.md` + новые/обновлённые карточки идей при необходимости + Journal.

### Чек-лист

- [ ] M1. Зафиксировать календарный месяц, дату среза, версию исходников/снимков и полноту по каждому из трёх роботов.
- [ ] M2. Провести **исследовательско-информационный обзор**: новости трейдинга и алготрейдинга, новые торговые идеи и стратегии, научные статьи, профессиональные публикации/форумы, количественные исследования, AI/ML и другие технологии, новые рыночные инструменты, изменения ликвидности/микроструктуры и возникающие торговые возможности. Отбирать значимое, а не пересказывать все новости. Для каждой содержательной находки указать первоисточник, дату, проверенный факт, гипотезу преимущества, применимость к MOEX/нашим инструментам, ограничения и следующее действие.
- [ ] M3. Сопоставить новые идеи с V1–V24 и ранее отвергнутыми исследованиями; без повторов «с нуля» и без заявления о доказанной прибыльности до теста.
- [ ] M4. По обезличенным сделкам V20 сделать таблицу **Shallow / OBV / Inside / портфель**; проверить reconciled gross/net ₽, расходы, закрытые сделки, PF, net R, стопы, DD и полноту. Срезы по инструментам, причинам выхода и перекрытию рисков — при наличии данных.
- [ ] M5. Сопоставить фактические результаты с предыдущими периодами и frozen V20 **описательно**, отмечая различия рынка, исполнения и малую выборку.
- [ ] M6. При наличии содержательных идей отобрать до 1–3 гипотез **по качеству механизма**, не по заведомо раздутому PF; отметить необходимые данные и ожидаемый эффект. Если достойных идей нет, зафиксировать отсутствие подтверждённых кандидатов, не придумывая их.
- [ ] M7. Записать факты, гипотезы и решения в Journal, обновить карту открытых исследований и план следующего месяца, опубликовать отчёт в GitHub.

**Смысл:** статистика портфеля не равна механической сумме процентов счетов или простому сложению PF. Net PF = сумма положительных net результатов закрытых сделок / модуль суммы отрицательных net результатов. Если для расчёта нет обеих сторон — `NOT_AVAILABLE` / `UNDEFINED`, не 0. R — сумма нормированных результатов конкретных сделок, **не % доходности портфеля**. Для Max DD ₽/% нужна отдельная хронологическая серия equity/капитала; trade-close DD в R указывать отдельно и не называть финансовой просадкой счёта. Для стопов различать исходный SL, trailing/другие стопы. Незакрытые позиции учитывать отдельно, не приписывать им realised P&L.

**Пустые данные:** `0` — только если проверенный полный снимок действительно содержит ноль сделок; иначе `NOT_AVAILABLE` или `PARTIAL`. Первый период LIVE может быть слишком коротким для выводов о прибыльности — это отдельный вывод, не провал проекта.

### Итог месячной карточки (обязательные четыре строки)

1. **Реальный результат:** net ₽, PF, DD, закрытые сделки, **статус достаточности данных**.
2. **Что изменилось:** фактически подтверждённые сдвиги по роботам/рынку.
3. **Новые возможности:** идеи/ссылки и объяснимые гипотезы, отдельно от результатов тестов.
4. **Решение:** что проверить, отклонить или наблюдать в следующем месяце.

**Приёмка месяца:** исследовательский обзор, включающий существенные новости и новые возможности, + таблица с реальными числами **или явными NOT_AVAILABLE/PARTIAL** + решения/приоритеты + Journal. Если торгового снимка нет, исследовательская часть может быть выполнена, а аналитика V20 остаётся `HOLD_DATA` — не выдавать весь месяц за полностью закрытый.

## 2. TRL-02 — ЕЖЕКВАРТАЛЬНЫЕ ИССЛЕДОВАНИЯ (январь / апрель / июль / октябрь)

**Результат:** `reports/TRL-QUARTER-YYYY-QN.md` + карточка новой стратегии и, если есть обоснование и данные, карточка улучшения V20 + Journal. Полное исследование планируется **в одном обозначенном месяце** (январь/апрель/июль/октябрь), а не автоматически на весь квартал. Месячный TRL-01 идёт независимо.

### Чек-лист

- [ ] Q1. По накопленным источникам TRL-01 и реестру прежних исследований выбрать **минимум одну новую стратегию при достаточных данных**; для V20 — только потенциальное улучшение с конкретным обоснованием. Сформулировать механизм прибыли. Новая система не обязана походить на V20.
- [ ] Q2. Зафиксировать исходники, код/commit, торговые правила, инструменты/TF, период, расходы, допущения и frozen baseline до проверки результатов.
- [ ] Q3. Выполнить один первоначальный backtest на проверенной истории; показать сделки, PF, net R, Max DD, годовые/инструментальные разрезы.
- [ ] Q4. Провести проверку устойчивости по годам/инструментам/вариациям параметров, чувствительность к расходам и проверку причинности/исполнения (NEXT_OPEN или иной строго объявленный контракт).
- [ ] Q5. Провести независимую проверку там, где это реально возможно; пометить уже исследованный 2018–2026 как `OOS_COMPROMISED`, если независимости нет. **Не объявлять новый TRUE OOS** только из-за повторного запуска.
- [ ] Q6. Для улучшения V20 сравнить baseline vs candidate **на одинаковых данных, расходах, логике исполнения и риске**; учесть портфельный эффект и возможное ухудшение других показателей.
- [ ] Q7. Выдать **отдельное решение** по каждой гипотезе: `REJECT`, `CONTINUE`, `CANDIDATE` или `HOLD_DATA`, записать причины и следующий шаг в Journal; обновить список приоритетов.

## 3. ГОДОВЫЕ ИТОГИ — ДЕКАБРЬ (первый раз декабрь 2027)

**Результат:** `reports/TRL-ANNUAL-YYYY.md` + план следующего года + Journal. **За 2026 год TRL не подводит годовые итоги.** Первые итоги — **декабрь 2027 (предварительно)**, окончательная финансовая сверка 2027 после получения декабрьских данных в январе 2028.

### Чек-лист

## 4. Общий формат итогового отчёта (всех трёх уровней)

В начале **одна страница для принятия решения**:

1. **Период и покрытие** — источник, дата, SHA, COMPLETE/PARTIAL/NOT_AVAILABLE.
2. **Главные числа** — только действительно подтверждённые метрики, единицы ₽/R/% и вид P&L.
3. **Что выяснили** — факты отдельно от гипотез.
4. **Что не знаем** — качество/независимость данных, ограничения, малое число сделок.
5. **Решение и следующее действие** — владелец, задача, статус.
6. **Доказательства** — ссылки на GitHub, исходники, отчёты, номера Journal и версии.

Статусы задачи: `OPEN`, `IN_PROGRESS`, `PASS`, `PARTIAL`, `HOLD_DATA`, `REJECT`. Не приписывать `PASS` конкретной гипотезе на основании одного высокого PF.
